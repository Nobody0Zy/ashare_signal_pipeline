# 知识面 04 · 工程执行经验（agent 协作与验证）

> 创建日期: 2026-09-30
> 定位: 把实验「交给 agent 执行」时的**可复用工程经验**。与具体实验结论无关，任何谱系都用得上。
> 主要来源: `strategy_explore` 仓库 `design/v4/agent_execution_lessons.md`（v4_0 自动化推进的 12 问题复盘 + v4_1 独有风险）、v5 实施期间的实际教训。
> 使用方式: 编写作执行文档（prompt / implementation_plan）前后对照检查。

---

## 1. 文档组织与执行分工

### 1.1 三层文档职责边界

| 层级 | 内容 | **不含** |
| :--- | :--- | :--- |
| 顶层 overview | 全局依赖、执行顺序、接口契约、风险、决策点 | 具体代码改动细节、实验参数表 |
| pre_refactor | 哪个文件改什么、验收标准 | 实验策略、预期效果 |
| experiment | 实验矩阵、变量对比、评估口径、回溯分析 | 代码实现细节 |

**为什么要分**：把「代码改动」与「实验策略」混在一份文档里，会导致 agent 在执行时越界改实验设计，或按实验目标改代码。

### 1.2 分支管理：扁平顺序优于层级嵌套

| 项 | 做法 |
| :--- | :--- |
| 原则 | 每个阶段一个独立分支，做完合回 `main` 立即删除 |
| 命名 | `code/{version}_{stage}`（如 `code/v4_1_pre_refactor`） |
| 不保留 | 中间集成分支（如 `code/v4_1`） |

**优势**：合并只有 1 层；出问题回退简单；`git branch` 一目了然。

> v5 的实际做法与之略有不同（长期分支 + 收尾后合并删除），见 `strategy_explore` 仓库 `design/v5/discussion/closeout_map/01_v5_first/02_v5_plan.md`。两种都可行，关键是**分支与「阶段」一一对应、合并后即删**。

## 2. 代码编辑类问题（交给 agent 改代码时）

### 🔴 L-01 oldString 必须与文件逐字一致

| 项 | 内容 |
| :--- | :--- |
| 现象 | prompt 用 `# 改动前` 注释假设中间状态，但文件实际未改，导致替换失败、整个 Phase 阻塞 |
| 规避 | ① oldString 从文件**逐字复制**，不手写；② 禁止 `# ... 现有字段不变 ...` 这类省略写法；③ dataclass 改动要展开到类定义的完整闭包 |

### 🔴 L-02 同区域改动必须合并为单次替换

| 项 | 内容 |
| :--- | :--- |
| 现象 | 两个替换作用于相邻区域，并行提交时后者找不到目标 |
| 规避 | 同文件相邻改动合并为**一个** oldString/newString，覆盖完整区域 |

### 🟡 L-03 重复文本需要唯一上下文

| 项 | 内容 |
| :--- | :--- |
| 现象 | 单行文本在文件中出现多次，无法唯一定位 |
| 规避 | oldString 包含前后 3~5 行唯一上下文 |

### 🔴 L-04 跨文件语义耦合必须原子修改

| 项 | 内容 |
| :--- | :--- |
| 现象 | 先加字段、后改消费方，中间状态代码不可执行（`AttributeError`） |
| 规避 | 所有相关 Python 代码改动为**单一批次**；新增配置字段 + 所有消费方同批落地 |

## 3. 命令与脚本类问题

### 🔴 L-05 命令模板必须使用真实 CLI 签名

| 项 | 内容 |
| :--- | :--- |
| 现象 | 文档写 `--steps 1,2`，实际 CLI 是 `--mode smoke --step 1 --state-file xxx`，agent 生成的命令全部无法执行 |
| 规避 | 执行文档中必须包含**真实的参数签名与验证命令模板**（见 [01_pipeline_contract.md](01_pipeline_contract.md) §3） |

### 🔴 L-06 不要在单行 `python -c` 里写循环

| 项 | 内容 |
| :--- | :--- |
| 现象 | 混用 `for` 与 `;` → `SyntaxError`（Python 不允许 `;` 后跟 `for`） |
| 规避 | 使用多行语法、独立 `.py` 文件，或写成无循环的表达式 |

### 🔴 L-07 验证旧行为必须走 YAML 加载路径

| 项 | 内容 |
| :--- | :--- |
| 现象 | 重构改了 dataclass 默认值，`PipelineParams()` 裸构造与 `from_yaml()` 结果不同 |
| 规避 | 验证旧行为用 `load_params()` / `from_yaml()`；新旧行为用不同 state-file |

### 🟡 L-08 长内联脚本的编码与长度

| 项 | 内容 |
| :--- | :--- |
| 现象 | ① PowerShell 内联 Python 中的中文被转成 `??`；② 超过 10 行的内联脚本容易出错 |
| 规避 | 优先短命令、独立脚本或日志重定向；对 GBK 数据按列位置/Unicode 转义处理 |

## 4. 验证环境与数据保护

### 🔴 L-09 严禁用删除目录来「重置环境」

| 项 | 内容 |
| :--- | :--- |
| 现象 | 验证脚本写 `Remove-Item outputs -Recurse -Force`，删掉全部历史运行与分析报告 |
| 规避 | 用**独立 state-file** 隔离；执行文档中显式禁止任何破坏性清理 |

### 🔴 L-10 备份不要放在删除范围内

| 项 | 内容 |
| :--- | :--- |
| 现象 | 备份写到 `outputs/` 下，紧接着被同批清理删掉 |
| 规避 | 备份放到删除范围之外（如项目根目录的独立目录） |

### 🔴 L-11 共享中间产物的验证必须串行

| 项 | 内容 |
| :--- | :--- |
| 现象 | 两条验证路径输出目录不同，但共享 `data/processed/`、`data/slices/`；并行会争抢同一文件 |
| 规避 | 串行执行；每条路径独立 state-file；必要时明确说明「不得并行」 |

### 🔴 L-12 分支输出文件冲突

| 项 | 内容 |
| :--- | :--- |
| 现象 | 同一 step 的两个分支写入同一输出文件，列结构完全不同；配合幂等跳过会读到错误结构 |
| 规避 | 分支用不同 state-file / 不同文件名隔离 |

## 5. 语义与一致性

### 🟡 L-13 `fillna` 参数的真实语义

| 项 | 内容 |
| :--- | :--- |
| 现象 | 参数名暗示「是否填充 NaN」，但实际上 `inf` **始终**会被替换为 `NaN`（第一步），`fillna` 只控制最后是否补 0 |
| 规避 | 文档中显式说明双步骤逻辑；不要把 `fillna=False` 理解为「不做 NaN 处理」 |

### 🟡 L-14 多分支返回结构必须一致

| 项 | 内容 |
| :--- | :--- |
| 现象 | 某分支不产生某些文件，导致 `details` / `output_files` 键缺失，下游需按分支特判 |
| 规避 | 同一步骤多分支的 `details` / `checks` / `output_files` **键必须一致** |

## 6. 交付与流程

### 6.1 阶段结束做 git checkpoint

1. 先**汇报**分支/工作区状态。
2. 提出**分组提交建议 + 中文 message**，取得确认后再提交。
3. 生成的运行产物保持 ignore，不提交工件；只提交文档/代码/登记的跟踪文件。

### 6.2 收尾阶段不提交

收尾流程（[06_closeout_playbook.md](06_closeout_playbook.md)）只输出**分组建议**，不执行 commit；提交由人工确认。

### 6.3 长任务的状态检查

1. 全量 step 跑动时，**优先读 state 文件**判断进度（step 状态只在整步成功后落盘）。
2. 低频检查（约每 5 分钟）优于紧轮询。
3. 用进程 CPU/内存区分「仍在计算」与「已失败」。

### 6.4 中文提交信息

Windows PowerShell 下给 git 写中文 message 时，命令行参数可能被编码转换破坏。**用文件承载 UTF-8 消息、再 `git commit -F`**，提交后用工具校验真实内容。

---

## 7. 一句话总结

第一轮实验中，**agent 执行出的错误几乎都不是「算法错」，而是三类**：① 编辑目标定位不准；② 命令与文档不一致；③ 验证时破坏了数据或不隔离。因此给 agent 的执行文档，重点不在「讲清要做什么」，而在**把这三类错误的前置条件写死**。
