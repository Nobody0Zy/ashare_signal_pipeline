| 编号 | 问题 | 结论 | 理由 |
| :---: | :--- | :--- | :--- |
| Q1 | 运行间对比是否进报告 | **不进**，改用 `tools/compare_runs.py` | 进报告会破坏幂等（A-6）、破坏归属唯一（一份报告描述一次运行）、破坏归档稳定（历史报告内容随新运行变化） |

| Q4 | 长度上限 | 不设硬上限，超限只打 `[HINT]` | 硬上限会逼迫删减必要证据；提示足以引起注意 |
| Q5 | 中英双语标题 | 不需要 | 单语更紧凑；关键字段保留英文原名便于对照代码 |
| Q6 | 领导版风险提示 | 需要，独立成行，置于行动项前 | 风险不能埋在结论里 |
| Q7 | 领导版 KPI | 基线 4 个锁定，支持追加 | 既要可比（基线固定），又要可扩展（agent 自定义） |
| Q8 | 极值（min/max）是否报 | **必报**，且与 IQR 同表 | 极值决定最坏情况损失与策略容量；只报极值会被带偏，只报 IQR 会丢失尾部风险 |
| Q9 | 漂移是否"判定" | 只报"提示"，附阈值说明 | 1pp/5pp 是经验约定，无 p 值、非自适应，写成判定属伪精确 |
| Q10 | 100 组首尾组噪声如何处理 | 正文用秩相关 + 首/末 10 组均值；图表直接显示首末 | 单组约 500 条，均值易被极端样本带动；但图表不必人为截断，读者看整体 |
| Q11 | 领导版是否展示 100 组明细 | **不展示**，明细落 CSV | 300 行表格会淹没结论；图 + 抗噪汇总已足够 |
| Q12 | T2/T3 信息放哪 | 数据卡（T2）+ 参考页（T3），报告只引用 | 复制进每次实验报告会导致定义过期且无从察觉 |

## 3. 被否决的方案

### 3.1 兼容策略

| 方案 | 否决原因 |
| :--- | :--- |
| A. 旧名永久装新内容 | 两份文件同内容必然分叉；且固化"文件名即契约"这一根因 |
| B. 直接废弃旧名 + 改 bagging | 一次性打断 ensemble 与既有文档引用，风险集中且无过渡证据 |
| **C. 清单契约 + 一版弃用 alias（采用）** | 用机器可读清单把"产物"变成显式契约；alias 有明确死期，既解根因又不制造硬断裂 |

### 3.2 信息承载

| 方案 | 否决原因 |
| :--- | :--- |
| 单份报告装全部信息 | 受众冲突：工程细节污染实验结论，实验解读淹没工程排障 |
| 三份报告装全部信息（含 T2/T3） | 体量膨胀；定义过期无从察觉；交叉核对成本高 |
| 增加更多报告（如"数据报告""模型报告"） | 只增加维护面，不增加信息；T2/T3 已有专门载体 |
| **3 报告 + 1 数据卡 + 1 参考页（采用）** | 覆盖率与维护成本的最小集 |

### 3.3 图表

| 方案 | 否决原因 |
| :--- | :--- |
| 领导版新增"五分组柱状图" | 100 组图信息更全；新增图需要新增绘图代码，且与 100 组图重复 |
| 领导版只放 1 张 100 组图 | 三集合无法对比，测试集证据不足 |
| **领导版放 5 张（train/val/test/合并/预测柱状）（采用）** | 三集合可比 + 预测分桶可验证 + 折线柱状互补 |
| X9 本迭代加漂移条形图/月度柱状图 | 表格已足以判定阈值；先交付，图留 v1.2 |

### 3.4 事实表

| 方案 | 否决原因 |
| :--- | :--- |
| 每份报告各自读 CSV/state | 同一指标三处算法，必然漂移 |
| 渲染器做少量统计 | 破坏"零计算"不变量，报告数字无法追溯 |
| **单一事实源 + 渲染器只格式化（采用）** | 可追溯、可幂等、可断言 |

## 4. 关键设计点为什么这样定

### 4.1 为什么 `schema_version` 是 `report-summary/1` 而不是时间戳

版本号用于**契约兼容判断**（消费方可拒绝不认识的版本），时间戳只能用于展示。语义化整数便于比较。

### 4.2 为什么 `drift_hint.thresholds` 写进事实表而不是渲染器

两个理由：① 阈值是**判定口径**，属于数据语义而非排版；② 渲染器若自己写死 1.0/5.0，改阈值就要改代码，且历史报告无法解释当时用的阈值。

### 4.3 为什么 X9 的 `idxs` 要从 `sample_id` 解码

`predictions.csv` 不含 `idxs` 列（只有 `sample_id` / `signal_date`）。若为此改 step6 输出，就违反"step 语义零变更"。解码规则见 `data_prep/ids.py::parse_sample_id`，是既有公开函数。

### 4.4 为什么 E8 要区分"实际计算特征数"与"入选特征数"

报告读者看到"50 个特征"会以为特征工程只算了 50 个，从而误判 41 分钟耗时的合理性。实际是 **324 个计算 → 筛到 50 个**。E8 的核心价值就是把"耗时"与"工作量"挂钩。

### 4.5 为什么 M1 要求逐字节一致

`report/experiment.py` 是从 436 行的 `render_markdown_report` 搬运而来。若 M1 顺带改文案，就无法区分"搬运引入的偏差"与"有意改动"。M1 只搬不改，M4 才改结构。

### 4.6 为什么 K1 的 4 个 KPI `locked: true`

领导版被 agent 频繁自定义。若不锁定，某次 override 删掉 Spearman 或替换成别的指标，跨期汇报就失去可比性。锁定 4 个 + 允许追加，是"可比性"与"扩展性"的折中。

### 4.7 为什么 `> 简单说：` 不得引入新数字

提示块的定位是"翻译"而不是"补充证据"。一旦允许新数字，就会出现"正文没有、提示里有"的不一致，且该数字不受事实表约束（违反不变量 4）。

### 4.8 为什么 `holding_clean` 覆盖问题只在报告层补救

本迭代的边界是"报告层"。修 step2 会改变产物语义，需要同步更新 `docs/01_pipeline_contract.md`、`docs/07_step_acceptance_criteria.md` 与历史回归断言，属于独立里程碑。因此登记为 PR-001，报告层只做"两次行数 + 警告"的告知性补救。

---

### 4.9 为什么 `label_span_stats` 是**条件必填**（samples 必填、holding_file 可空）、且修复后仍保留

**为什么是"条件必填"而不是进 38 个必填键**

1. 它描述的是**标签口径事实**：`samples` 模式下必然可算，`holding_file` 模式下 `horizon_days=0`、无标签文件，写 `null` 才是正确表达。
2. 若纳入 `A-1` 的 38 个必填键，`holding_file` 场景会因"键存在但值为 null"与"键缺失"难以区分；因此把强制性交给 A-29，A-1 只管键存在性。
3. 对历史 summary 的兼容：旧 summary 无此键时，只有 `samples` 模式会 fail（A-29），这正是我们希望暴露的——旧产物需重算一次。

**为什么修复后不删**

| 阶段 | 该键的含义 | `policy` |
| :--- | :--- | :--- |
| v1.1.1（未修复） | 跨停牌样本的**污染比例** | `uncapped` |
| v1.2（B：加标记） | 被标记为长跨度的**样本比例** | `uncapped` |
| v1.3（A：硬过滤） | 被 `max_calendar_span_days` **排除的样本比例** | `capped:60` |

数字不会随修复消失，只会换含义。修复本身要回答"排除了多少样本、结论变了多少"，这正是该键提供的量；删掉它等于让修复效果无法量化，且历史 summary 无法重渲染。

**为什么由事实表承载**（而不是数据卡）

严格按 T2/T3 分层，它属于 T2（`samples_id` × label 的属性）。但报告 X1.3 需要就地展示这一行，而渲染器不得现算（不变量 2 / A-7）。折中：事实表提供渲染所需物化值，数据卡 §D4 只保留 coverage，不复制 span 数字，避免同一数字两处定义。

## 5. 文档演进：单文档 → 四件套

### 5.1 首版（2026-11-13，`design.md`，1072 行）

单文档包含：目标、事实基准、架构、契约、报告规范、可读性、里程碑、验收、风险、修订记录。

### 5.2 为什么不够

按 v1.1 的经验，一个**未参与设计**的工程 agent 需要四类信息，且它们的读者与更新频率不同：

| 信息类型 | 首版位置 | 问题 |
| :--- | :--- | :--- |
| 规格（做什么、口径是什么） | 混在 §0–§6、§9 | 与施工细节交织，难以定位"这一条要不要做" |
| 施工顺序（先改哪个文件） | 里程碑表只有"关键动作"一句 | agent 不知道在哪个函数里加 |
| 执行边界（能不能改、错了怎么办） | 无 | agent 会自行补充字段/图表/结论 |
| 依据（为什么这样定） | 混在 §11–§13 | 实施时不需要读，却占了 1/3 篇幅 |

### 5.3 差距闭合（对应 `implementation_plan.md` §0.4）

首版识别出 12 项实施缺口（G1–G12）：文件白名单、逐文件改动、函数签名、字段 JSON 路径、X9 计算定义、CLI/exit code、降级矩阵、golden 方法、数值锚点、断言→位置映射、回滚点、禁止发明清单。

闭合方式：

| 缺口 | 闭合产物 |
| :--- | :--- |
| G1/G2/G11 | `implementation_plan.md` 每里程碑「具体动作」表 + 回滚点 |
| G3/G4/G5/G6/G7 | `experiment_design.md` §2.2 / §3.1–§3.5 / §2.2 / §3.5 |
| G8/G9 | `implementation_plan.md` §3.3 golden 命令 + `baseline_v1.1.0.json` |
| G10 | `implementation_plan.md` §9 断言映射表 |
| G12 | `code_agent_prompt.md` §7 禁止发明清单 |

### 5.4 结论

四件套（design / plan / prompt / memory）+ 一份 baseline JSON + README 导航，与 v1.1 的实践一致：**规格可独立评审、计划可独立执行、边界可独立仲裁、依据可独立追溯**。

## 6. X10 结论内容基线

`X10.1` 的四组结论来自 v1.1 demo 实测，实施时按事实表现算，但**分组维度与条数**保持如下骨架：

| 视角 | 条数 | 必含要点 |
| :--- | :---: | :--- |
| 统计 | 4 | 排序能力与强度；train→test 衰减及归因（分布变化 vs 过拟合）；分组年份集中度；样本独立性（标签重叠） |
| 交易 | 4 | 过滤器价值 > 预测价值；阈值非单调（前 10% 回落）；收益依赖少数月份；未计交易成本 |
| 数据与标签 | 3 | 标签左偏（均值 vs 中位）；重叠是采样与持有期共同结果；多标签只用了 1 个 |
| 工程 | 3 | 模型容量非瓶颈（早停轮次）；特征贡献集中度；特征计算成本 |

`X10.2` 方向清单（P0–P2）：

- P0：换标签验证、分 regime 评估、计交易成本、重叠感知显著性检验
- P1：去重采样、特征中性化、排序目标、组合视角
- P2：多标签联合建模、跨样本集外部检验

`X10.3` 反模式：单期 Spearman 判优劣、未处理重叠做显著性检验、把"只留前 10%"当精选、用均值描述左偏 target。

## 7. agent 常见失败模式（本迭代预防）

| 失败模式 | 表现 | 预防 |
| :--- | :--- | :--- |
| 顺带改 step | "顺手"修 `holding_clean` 覆盖 | prompt §6 禁做 12 条 + B7 阻塞 |
| 一次大改 | M1 搬运时顺手改文案 | M1 golden 逐字节 + prompt §3.2 不预读 |

| 破坏幂等 | 在报告里写"本次比上次好" | A-22 |
| 污染证据 | 用默认 `--report` 覆盖历史文件 | prompt §5 第 3 条 |
| 重建数据 | 为了让 hash 对上而重跑 build_samples | prompt §6 禁做 4 + B8 阻塞 |
